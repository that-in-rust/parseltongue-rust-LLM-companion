# Backlog ideas 01: Can a 100 MB Rust model reach 98% agreement?

2026-11-08 | Status: **open, disputed, not tested at the proposed scale.**

The product question is whether a local model can **build the public-interface dependency graph of a previously unseen Rust repository** well enough for a coding agent to navigate it. The research bet is specific: train a 100 MB model on the top 100 Rust repositories and their tooling-generated sample outputs, going over the data roughly 40 times. Could it then match 98% of what deterministic Rust tooling answers?

Amul's response to the skeptical assessment below was **"I disagree with you"**. This entry keeps the original bet on the backlog. It is not a decision to reject the experiment, replace it with a narrower one, or claim that the target has already been achieved. No more specific grounds for the disagreement were given.

## What is being disputed?

**The case for trying it:** the model need not converse about Rust in general. The output vocabulary is small, Rust tools can supply structured examples, and many sites in different projects exercise the same binding rules. A hundred repositories can yield many more than a hundred training examples. The CLI can give the model source spans, active build settings, and competing declarations. If the learned part generalizes, it could recover useful edges without running the teacher during inference. How much of the map can be learned this way is an empirical question.

**The assistant's assessment:** I would bet against that recipe matching rust-analyzer on 98% of arbitrary semantic queries on unseen repositories. I would fund a narrower bet: a 100 MB CPU helper, working with Parseltongue's CLI and index, could reach 98% precision on particular public-interface relations. That is a credible experiment, not a measured result. The product need not reproduce rename, diagnostics, completion, and arbitrary expression typing to make the public-interface graph useful. Equally, success on that graph would not demonstrate parity with all those operations.

| Claim to test | How to read the result |
| --- | --- |
| 98% agreement with rust-analyzer across semantic queries | Define the requests, configurations, and scoring unit in advance. A result for one request family does not establish parity for others. |
| 98% precision on emitted `parameter_type`, `returns`, and `reexports` edges | Check the exact source item, relation, and destination. Report recall and coverage for each relation; an extractor can achieve high precision by emitting very little. |
| The model adds value where deterministic rules abstain | Measure additional confirmed bindings, wrong bindings, unverified predictions, and abstentions on those sites. Score the model-enabled system against the same host with learning disabled. |
| The tool operates on CPU under 100 MB | Distinguish weight-file size from peak resident memory. Measure the shipped inference process and report the full CLI plus any required subprocesses separately. Neither follows from the number of repositories or epochs. |

## What forty passes can and cannot teach

In the preceding review, the same Rust source compiled twice with different active features. In the default build, `build() -> Sender` returned `portable::Sender`. With the `fast` feature enabled, it returned `fast::Sender`. The signature text did not change. If a predictor sees *only those bytes* and must select one target, it can get at most one of that balanced pair right. That is a 50% bound **on this pair**, not on the corpus, and not a bound on a model given the feature profile. See the [Rust Reference on conditional compilation](https://doc.rust-lang.org/reference/conditional-compilation.html).

Repeating identical labels can improve fitting; it cannot supply a configuration omitted from the input. A useful comparison is to spend part of the training budget on examples where one relevant fact changes: toggle a feature, redirect a re-export, introduce a same-named type, or move a declaration while preserving its public path. Ask the teacher which answers changed and which stayed stable. In particular, do not give the student the teacher-resolved destination as a retrieval hint. [Scaling Data-Constrained Language Models](https://arxiv.org/abs/2305.16264) finds diminishing returns from repeated data in its pretraining setting; it does **not** establish the optimal number of epochs for this supervised Rust task.

## What the repository demonstrates today

The [original binding experiment](../experiments/tiny-reexport/learned-binding/pretrained/README.md) used a pretrained encoder with scoring heads, not a full generative graph model. On five held-out releases, a same-module rule found 56 rust-analyzer-confirmed bindings. The model added no accepted bindings on the 47 sites where the stronger rules abstained. This is one return-type resolution task; it is not the proposed 100-repo training run.

In the [fresh-crate follow-up](../experiments/tiny-reexport/learned-binding/pretrained/weight-edit/README.md), 25 sites remained after the rules abstained: **7 confirmed bindings, 1 unverified prediction, 17 abstentions**. The original and weight-edited models made the same acceptance decisions. The edit did not earn the seven recoveries. Several sites were related; they are not seven independent reasoning mechanisms. The Tokio confirmations apply to the feature profile used for evaluation.

The edited checkpoint was **17,454,319 bytes on disk**; its whole CPU inference process peaked at **90,456,064 bytes** on the reported setup. This excluded offline rust-analyzer and Python evaluation. It shows that useful learned recovery under the process limit is possible for a narrow task. It establishes neither 98% graph accuracy nor the memory footprint of an entire large-repository indexer. Conversely, these small negative and positive results do not settle what training on 100 repositories for 40 epochs could achieve.

## Related B12/B13 commentary

The [B12/B13 research](Deep-Insight-05.md) made the graph easier to picture: expand a folder connection to file dependencies, then to an interface and its source evidence. Folders can be a navigation view over the two product levels, not a third prediction task. The following qualifications from the review affect both the training labels and what an agent may safely infer:

1. **Cache syntax separately from bindings.** File bytes, model revision, and schema version are not enough to key a resolved edge. Include the build context and relevant imports, re-exports, and dependencies. In the [pinned semver experiment](../experiments/public-interface-semver/README.md), enabling `serde` added six implementation edges at the same commit. An unchanged file can need relinking without needing reparsing.
2. **Filter before rolling up edges.** If `client/` already imports a type from `policy/`, and a proposal would add a call between those folders, report one observed import and one proposed call. Labeling the whole connection "extracted" conceals the design change. A direct file fact such as `mod child;` also exists when `child.rs` exports no interface; not all file edges are sums of public edges.
3. **Name search is not definition lookup.** `find Sender` can correctly return two candidates without resolving the occurrence under the cursor. Likewise, an impact neighborhood is not an exhaustive list of references. [LSP definition requests](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/language/definition.md) specify a source position. The [SCIP schema](https://raw.githubusercontent.com/sourcegraph/scip/main/scip.proto) is useful for occurrence and symbol labels, not a guarantee that an export contains every receiver type or runtime call.
4. **An unseen site is not an abstained site.** Lazy body analysis can say what a scanned function calls while missing callers in unscanned files. Distinguish no matches in the analyzed scope, target unresolved at an observed site, files not analyzed, and response truncated. In particular, an empty reverse query is not evidence that deleting the interface is safe.
5. **Keep public contracts distinct from implementation dependencies.** In B13's `retry` example, `Client` is public but its `policy: Box<dyn RetryPolicy>` field is private. That relationship belongs on the implementation map, not in the list of fields downstream code may access. A statically identified trait method and a possible concrete dispatch target are different claims; the example's `0.93` is illustrative, not calibrated confidence.

There is already a useful product test independent of LSP parity: the `semver::Error` reverse query returned **five public inherent signatures** that can return that type, with source locations. It tells a maintainer which contracts to inspect, not that those functions call each other or that five downstream programs will break. Extend the test: change a re-export or feature without changing the consumer file; require the stale edge to disappear, the replacement to carry evidence, unscanned callers to remain unknown, and the proposed map to remain separate from observed code. Run with the tiny model both off and on.

## The experiment that could settle the bet

1. **Keep the original recipe as an experimental arm.** Define what "top 100" means, pin revisions and tooling, and train on those repositories' labeled outputs. Compare checkpoints at 1, 4, 10, and 40 epochs on separate validation repositories. Do not remove the 40-pass arm just because the skeptical forecast predicts diminishing returns.
2. **Make generalization visible.** Split by repository family before training; keep forks, near-duplicate versions, and vendored copies out of the blind test. Record what was held out from our own supervised training without claiming knowledge of all upstream pretraining data. Keep one untouched test set until checkpoint selection is finished.
3. **Start with signature relations; test wider claims separately.** Score `parameter_type`, `returns`, and `reexports` first. Score body-level calls, receiver resolution, and any wider LSP request families in their own panels. A teacher's missing answer is not automatically a negative label. Pin features, target, and dependency versions and keep examples with multiple candidates or no correct candidate in the list.
4. **Separate algorithmic, retrieval, and learned contributions.** Compare rules alone with the same retrieval and rules plus the model. Also run a direct source-to-record model if testing the model-alone claim. Report how often the true target was retrievable at all. Compare repeated examples with configuration/alias contrasts at a comparable training budget; do not silently substitute a different experiment for the original one.
5. **Agree on the denominator before opening test results.** Publish per-relation precision, recall, answered-site coverage, unverified counts, and results by repository and hard-case family. Set a minimum useful coverage and a maximum wrong-edge rate beforehand. Measure the quantized artifact on CPU, including tokenizer, buffers, and host allocations; report any offline teacher cost separately. Training accuracy and artifact size are not substitutes for blind accuracy and peak RSS.

**Decision rule:** record exactly which claim the result supports. If the 40-pass model generalizes at the declared threshold, that counts against the skeptical forecast. If only the hybrid system meets 98% precision at useful coverage, credit the hybrid without claiming full LSP parity. If the set is too small or too many labels are unverified, keep the question open. A useful outcome can also be: "On unseen Rust repos this CPU helper recovered additional confirmed interface dependencies at the following precision, recall, and memory cost."
