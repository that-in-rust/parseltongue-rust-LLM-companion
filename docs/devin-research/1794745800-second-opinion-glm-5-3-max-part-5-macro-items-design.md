## Q1 — D1 to D7

**D1 (identity = stored occurrence key). Right.** The chain is a first-class part of `SemanticOccurrenceKeyValue` (`crates/parseltongue-core-row-types/src/lib.rs:110,118,137-146`), the full-graph validator round-trips it (`hld-materialization-core-records.rs:974-986`), and `validate_full_graph_input` → `validate_graph_input_records` (`:518-524`) rejects non-empty chains **only** under `OriginalTopLevelContainment` (`:682`, `:796`). The frozen codec already encodes chains (`namespace-frozen-identity-codec.rs:19`) and the DuckDB store persists them (`hld-materialization-duckdb-store.rs:1121`). Strongest alternative — identity = (invocation, arm index, ordinal in expansion) — is strictly worse: two keys for one fact, and the canonical key already exists in every span row (`syntax-span-extractor/src/lib.rs:506`).

**D2 (container = call site's file area/module). Right**, and it matches the expected graph (`itoa-expected-graph-nodes.json:457` — `"owner": "area:src/lib.rs"` on generated nodes). But note the current SQL derives the container from same-file ancestors (`original-item-graph-projection.sql:17-27,46-56`): reused as-is it yields a *virtual-file* area node. You must join `macro-expanded-item-table.macro_invocation_identity_record` (`syntax-namespace-input-extraction.rs:1072-1073`) back to the call site's file instead. Not optional — the ancestors view joins on `file_path` equality.

**D3 (nullable node field + `expands` edge). Half right.** `expands` (call→definition) is pure new information; both endpoints are already nodes; evidence site = the invocation occurrence; fits `HldEvidenceRowKey` (`hld-materialization-core-records.rs:226-231`). Take it. For "generated by", a **field is the more expensive option**: it touches `HldNodeInputRecord`, the DuckDB store schema, the publication facade (`namespace-pipeline-publication-facade.rs:250`) and the export verb. But a `generates` *edge* has a cost you didn't price: 45 rows the expected graph does not contain, which A3 ("no extra rows") will flag in part 7. Third option, cheapest and my lean: derive it — the node identity already *contains* the invocation digest; publish the digest→invocation mapping (it is `macro-expanded-item-table`'s key) and let `node_qualified_path_text` (D5) carry it for humans. If the published node set must be self-contained, then the field; not the edge.

**D4 (expanded-text range as identity, original range optional). Right, but undersold**: the expected graph anchors generated nodes' `source_evidence` in the macro **definition body** — all five `const _` share byte range 4164-4179 in src/lib.rs (`itoa-expected-graph-nodes.json:473-482`). So the original range is not agent convenience; part 7's exact-range comparison cannot pass without it. Where: `HldEvidenceRowKey` has exactly four fields and whole-key equality drives `ConflictingEvidenceRecord` (`hld-materialization-core-records.rs:745-748`) — do not extend the key. A side table keyed by evidence row key is the cheap home. And yes, a call-site column already exists on site rows: `site_originating_macro_invocation_identity` (`syntax-span-extractor/src/lib.rs:684`, set at `syntax-namespace-input-extraction.rs:1007-1014`); body sites also carry the chain (`body-value-read-records.rs:138`). The missing piece is only the expanded-range→definition-range mapping from `macro_token_origin_rows` (`syntax-namespace-input-extraction.rs:1033-1043`).

**D5 (labels). Right defect.** Labels are only checked non-empty (`hld-materialization-core-records.rs:788-790`); part 7 owns the symbolic mapping (SPEC README, "Labels and identities"). The impl-header text is already fetched as `impl_bridges` in the projection (`original-item-graph-projection.rs:60-75`), and macro-call text is `span_source_code_text` — no new data needed. Cheapest sub-part of the five.

**D6 (order). Mostly right; split 5d.** It touches three independent skips: calls (`original-call-resolution-records.rs:109`), reads (`body-value-read-records.rs:97-102`), signatures (`signature-type-edge-tests.rs:246-255` — the skip is in the resolver the test pins), imports (`use-import-edge-records.rs:102`). Reads first: its expected change is already specified (`test_itoa_reads_row_counts` says "until part 5", `itoa-source-acceptance-tests.rs:2277`).

**D7 (inactive generated: no node). Right** — same rule as originals (`original-item-graph-projection.sql:31-34`; `lib.rs:510-512` stores `cfg_inactive`).

## Q2 — identity stability

The invocation digest is `blake3` over the JSON of the call-site occurrence key (`syntax-namespace-input-extraction.rs:899-900`). Its parts: the unit key, which has **no path fields** (`core-row-types/src/lib.rs:84-89`); the call-site path, stored **relative** (strip package/workspace prefix, `syntax-namespace-input-extraction.rs:481-495`); byte range; span digest. So the digest, and the occurrence path `.parseltongue/macro-source/<digest>/expanded.rs`, are stable across checkouts and runs. The trap: the `macro_virtual_source_path` **field** is absolute (`unit_package_root_path` join, `:901-906`). Keep it out of identity; use `span_source_file_path`. Original items are relative today by the same strip (`hld-original-source-projection.rs:571-592`).

## Q7 — what you failed to ask

1. **The `const _` conflict is the real risk in 5a.** `impl_Integer` wraps its impl in `const _: () = {` (pinned `src/lib.rs:137`). The inventory classifies any span under a `CONST` ancestor as `body-evidence` (`original-item-graph-projection.sql:35-38`) — so all 16 `write`/`fmt` FNs from `impl_Integer` are nested under a CONST and would be excluded. The expected graph has them as nodes. The part file must rule: in an `items`-fragment expansion, CONST-initializer nesting from the macro wrapper does not demote an item to body evidence.
2. **Part 7 needs the original range published** (D4) or exact-range comparison fails by construction — decide the side table now.
3. **`generates` edges break A3** unless the expected graph gains them or they're excluded from comparison.
4. Virtual files have no missing-file/unowned-item check today — a silent gap, needs a typed check or an accepted-gap entry.
