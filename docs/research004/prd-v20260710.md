# Parseltongue: the Rust public-interface dependency graph

Product requirements for the Lossfunk research track. This revises the July current-state call-graph proposal. It is not a release announcement. The [README](../../README.md) describes the released multilingual tool. Scope below is the Rust experiment; the narrower three-route surface is its proposed interface, not a claim that the released server has only three endpoints.

## 1. Product decision

**Give a systems programmer a small, inspectable map of how the public contracts in a large Rust workspace depend on one another.** A coding harness should be able to use the same artifact to decide what source to read. It should work on an ordinary checkout: no PR, branch comparison, cloud model call or IDE session required.

Today one can search a name, retrieve code and traverse dependencies in Parseltongue. The new question is whether a post-trained, local open-weight model can build a more faithful public map than the existing Tree-sitter pipeline on unfamiliar Rust OSS. The map is the deliverable. The model is a proposed producer; the database is an implementation detail.

## 2. First user's job

The distinction between a contract and evidence about its implementation comes from [Enriching ISG for Better Reasoning](https://docs.google.com/document/d/16kOkMjqiaQU55Rk_50-dURShoPNx3WXmpCkmXDSLIDU/edit). The [Google Docs source register](../../docs-lossfunk/02-learned-graph-compiler-thesis.md#google-docs-research-sources) collects the underlying proposals.

A maintainer is changing a storage subsystem. One public function returns `Result<Page, storage::Error>`; another calls a private logger which also mentions `storage::Error`. A text search finds both. A useful graph tells the maintainer that changing the exposed error type can affect consumers of the first contract. It must not draw that conclusion about the second merely because both bodies mention the same name.

| Start here | I need to know | Evidence I can inspect |
|---|---|---|
| Exported function or trait method | What do I have to name, satisfy, accept or return to use this? | Effective public path, signature, referenced type/trait definitions, and configuration. |
| A type or trait | Which public contracts depend on it, including through aliases? | Reverse of the same typed facts, with use sites; not an independent guess. |
| A public entry point | What could it call? How could this value cross a boundary? | Direct calls, input/output type roles and optional private path witnesses. Unknown dispatch stays unknown. This is navigation, not full control/data-flow proof. |
| An approximate name or source span | Can I go from source to the graph and back? | Stable symbol identity plus revision-specific source ranges. Absence, inapplicability and unresolved evidence are different outcomes. |

## 3. Deliverables and release claims

1. A Rust-specific public-interface dependency graph generator with open weights on Hugging Face, accompanied by a model card, reproducible CPU settings and known failures.
2. A redistributable training dataset plus the code to generate labels, train, evaluate and serialize outputs. Use the proposed top 50 Rust OSS libraries under a frozen ranking rule; record revisions, licenses and build contexts. The application proposes Codex 5.6 xhigh as teacher, not ground truth.
3. An improved Parseltongue which indexes a Rust workspace with the generator and makes the resulting graph usable through local export, evidence inspection and the three read operations. Replacing the existing database or deleting existing released routes is not a prerequisite.

**Success is empirical.** Evaluate on *additional*, unrelated large Rust OSS repositories kept out of training and tuning. Compare typed node/edge precision and recall with frozen Parseltongue and a strong Rust-aware baseline; report abstentions and false dependencies by kind. Prefer **under 100 MB peak inference RAM on CPU**; report whole-tool peak separately. Measure the proposed **roughly 5%** export-to-source token ratio with a pinned tokenizer, and measure navigation correctness separately. None of these is a measured result here.

## 4. What the map must mean

| Requirement | Acceptance example |
|---|---|
| PRD-PUBLIC-001: effective exposure | WHEN a private module's public item is re-exported, THEN the public export SHALL lead to the actual definition. `pub(crate)` alone SHALL NOT create a downstream public path. |
| PRD-TYPE-001: typed facts | WHEN a public signature mentions a return type without calling any function, THEN the export SHALL contain a signature dependency with the return position, and the call endpoints SHALL NOT report a call for it. |
| PRD-PATH-001: direct versus derived | WHEN a public operation reaches another through a private helper, THEN a projected path SHALL retain its witnesses and SHALL NOT be labeled a direct public-to-public call. |
| PRD-CFG-001: configurations | WHEN two feature selections expose different definitions, THEN exports SHALL identify their configurations. Missing build evidence SHALL NOT become an unconditional relationship. |
| PRD-EXPORT-001: inspectable output | WHEN exporting a committed capture, THEN the CLI SHALL emit a versioned, deterministic graph with typed endpoints and source locators. A reader SHALL be able to follow either direction without invoking the model. |
| PRD-EVAL-001: honest comparison | WHEN reporting a gain, THEN use the same target schema, revisions and declared inputs; separate parser-guided from model-led runs, teacher labels from independent evaluation, and payload tokens from peak RAM. |

## 5. Scope lock

Rust-only analysis for the residency. No chat assistant, general-purpose reviewer, compiler replacement, historical diff, full runtime trace, new hosted service or mandated storage engine. Private details may supply evidence; they are not automatically public graph nodes. All in-scope source is accounted for irrespective of whether it can be understood.

The proposed HTTP surface is exactly `GET /code-entities-search-fuzzy`, `GET /forward-callees-query-graph`, and `GET /reverse-callers-query-graph`. The latter two return **direct calls**, not arbitrary dependencies. Typed non-call facts are delivered in the local graph export. Keep the existing capture guarantees below: stable identity, independent byte verification, partial-code diagnostics, and atomic current state. References below to language adapters apply to Rust for this track.

## 6. Meaning of Complete Capture

"Complete" does not mean that static analysis can perfectly understand every
byte or resolve every dynamic-language call. It means that the system never
silently forgets a file, loses a byte, hides malformed source, or presents a
database write as complete when it differs from the calculated capture.

For every discovered file, the capture pipeline must assign one internal state:

- `indexed`: parsed and captured successfully.
- `degraded`: partially parsed or partially resolved, with usable evidence retained.
- `unsupported`: discovered but not handled by a configured language adapter.
- `unreadable`: could not be read safely.
- `ignored`: excluded by repository or product ignore rules.

### 6.1 Three-class byte ledger

For every supported, readable source file, the exact immutable source snapshot
used by the parser must be partitioned into only three mutually exclusive byte
classes:

- `INTERFACE_CODE`: defensible bytes owned by an accepted file-level RootSpan after confirmed comment and conservatively rejected error bytes are removed.
- `COMMENT`: bytes conclusively identified by the language adapter as comments.
- `UNKNOWN_CODE`: every remaining byte, including unclaimed source, malformed or incomplete syntax, unsupported constructs, and whitespace not owned by a recognized RootSpan.

Classification precedence is:

1. Confirmed comment bytes are `COMMENT`, including comments inside an interface.
2. Remaining bytes owned by an accepted RootSpan are `INTERFACE_CODE`.
3. Every unclaimed byte is `UNKNOWN_CODE`.

Direct member entities such as methods and constructors are semantic overlays
inside their RootSpan. They must not contribute a second set of accounting
bytes. Parser `ERROR` regions may be classified conservatively as
`UNKNOWN_CODE`. Zero-width `MISSING` nodes are retained as diagnostics
because they contain no source bytes.

For a captured source snapshot of N bytes:

```text
interface_code_bytes + comment_bytes + unknown_code_bytes
    == calculated_source_bytes
    == persisted_source_bytes
    == N
```

For N greater than zero, the ordered ledger segments must begin at byte 0, end
at byte N, and contain no gap, overlap, or empty segment. An empty file has zero
segments and zero bytes in all three classes. Unknown code is an honest semantic
result, not an accounting failure.

### 6.2 Calculated-versus-persisted manifest

Before writing, the capture pipeline calculates a manifest containing source
bytes, class totals, row counts, and content hashes. The database transaction
must independently derive the corresponding persisted totals.

The transaction must abort and preserve the previous committed revision when:

- Captured source bytes and persisted source bytes differ.
- Ledger segments contain a gap, overlap, or out-of-bounds range.
- The three byte-class totals do not equal the source total.
- A persisted segment hash does not match its source slice.
- Calculated counts do not match persisted counts for any captured relation,
  including files, root spans, entities, source segments, parse markers, call
  observations, call candidates, call edges, call sites, and diagnostics.

Malformed source, unknown code, unresolved calls, and parser diagnostics do not
cause rollback when the bytes and rows are accounted for honestly.

### 6.3 CLI accounting surface

The CLI is required to provide:

- `parseltongue index <repository> --verify`
- `parseltongue verify --deep`
- `parseltongue inspect-file <path> --ledger`
- `parseltongue inspect-file <path> --diagnostics`
- `parseltongue capture-report --format table|json`

After indexing, the CLI must report:

- Capture revision and status.
- Discovered, ignored, unsupported, unreadable, and indexed file totals.
- The supported-readable file set included in exact byte accounting.
- Calculated source bytes and persisted source bytes.
- Interface-code, comment, and unknown-code byte totals.
- Calculated and persisted counts for every captured database relation.
- Files and byte ranges containing unknown code.
- Parse-error and zero-width missing-node diagnostics.
- A separate PASS or FAIL result for every exact accounting invariant.

Machine-readable output must use a versioned, deterministic schema. The three
HTTP query endpoints expose entities and calls, not the full accounting model.

## 7. Entity Model

### 7.1 First-class entities

The capture layer should recognize code units that users can meaningfully search for or call, including language-appropriate forms of:

- Functions.
- Methods.
- Constructors.
- Classes, structs, traits, interfaces, enums, modules, and similar named containers.
- Other named declarations when a language adapter can identify them reliably.

Public and private declarations are both captured. Visibility is metadata, not an inclusion filter.

### 7.2 Semantic ownership rule

The product uses semantic ownership rather than blindly exposing every nested syntax-tree node.

- File-level declarations are first-class entities.
- Directly addressable members such as methods and constructors are first-class entities.
- A function or declaration nested lexically inside another callable is not a separate MVP entity.
- Calls found inside such a nested declaration are attributed to the nearest captured callable owner.
- The original nested source location remains attached as evidence.

Example:

```text
file
`-- function ABC              captured entity
    |-- nested function X     owned by ABC
    `-- nested function Y     owned by ABC
```

If `X` calls `save_record`, the graph records `ABC -> save_record` and preserves the call site inside `X`. Parseltongue must not claim that merely defining `X` means its body executed; language adapters must distinguish an observed call expression from runtime certainty.

### 7.3 Entity keys

- Every entity returned by fuzzy search has a `key`.
- Clients must treat the key as opaque and must not construct it from filenames or line ranges.
- The same entity should retain its key when unrelated lines are inserted above it or its body changes without changing its qualified declaration identity.
- The current line range is mutable location metadata, not identity.
- Overloads and same-named members must remain distinguishable.
- A rename or move may produce a new key in this MVP. Cross-version rename matching belongs to future diff work.

The endpoint names remain compatible with the current README. This PRD does not preserve the README's line-range-based key format as a permanent product contract.

## 8. Call Relationship Model

### 8.1 Included relationship in HTTP call lookups

The forward and reverse HTTP call views expose only direct `CALLS` relationships and their unresolved observations. They are projections, not the complete public-interface graph.

Imports, type uses, inheritance, implementation, containment, and arbitrary dependencies may be used internally to resolve calls, but they are not call relationships in these two HTTP responses. The CLI public graph separately exposes typed contract dependencies.

### 8.2 Direct means one hop

- Forward calls answer: "What does this entity directly call?"
- Backward calls answer: "What directly calls this entity?"
- Neither endpoint performs transitive traversal.
- Neither endpoint accepts a hop count.
- Repeated calls to the same target are represented as one relationship with multiple call-site evidence records.

### 8.3 Resolution states

Static analysis is imperfect, especially in dynamic languages. Parseltongue must expose uncertainty rather than manufacture certainty.

Each forward relationship or unresolved call observation has one resolution state:

- `resolved`: one repository target is supported by the available syntax and scope evidence.
- `ambiguous`: multiple repository targets remain plausible.
- `external`: the call appears to target a dependency, runtime, standard library, or generated boundary outside the captured repository.
- `unresolved`: a call expression was observed but no defensible target was found.

Backward results may contain only relationships for which the queried entity is a resolved or explicitly identified ambiguous candidate. Exact and possible callers must be distinguishable in the response.

### 8.4 Evidence

Every resolved or ambiguous internal relationship must include at least one call-site evidence record:

- `file_path`
- `start_line`
- `end_line`
- `start_column` when available
- `end_column` when available
- `source_excerpt` or another bounded human-readable locator

A relationship without repository evidence must not be presented as resolved.

## 9. The Three API Contracts

All routes are read-only `GET` requests.

### 9.1 Fuzzy entity search

```http
GET /code-entities-search-fuzzy?q=authenticate
```

#### Purpose

Resolve an approximate user query into one or more current entity keys.

#### Required behavior

- `q` is required and must contain non-whitespace text.
- Search is deterministic fuzzy lexical search, not embedding or LLM search.
- Search considers entity name, qualified name, signature tokens, kind, and repository-relative path.
- Exact name and qualified-name matches rank above partial matches.
- Results include enough metadata for a user or agent to choose the intended entity.
- Results come from one committed capture revision.
- Empty matches return a successful response with an empty `entities` array.

#### Minimum entity result

```json
{
  "key": "opaque-entity-key",
  "name": "authenticate",
  "qualified_name": "AuthService.authenticate",
  "entity_type": "method",
  "language": "typescript",
  "file_path": "src/auth/service.ts",
  "start_line": 42,
  "end_line": 71,
  "signature": "authenticate(request: LoginRequest): Promise<Session>"
}
```

Pagination, vector similarity, full source retrieval, and advanced filtering are not MVP requirements.

### 9.2 Forward calls

```http
GET /forward-callees-query-graph?entity=opaque-entity-key
```

#### Purpose

Return what the selected current entity directly calls.

#### Required behavior

- `entity` is required and must be a key returned by fuzzy search.
- The response identifies the source entity.
- `callees` contains unique direct repository targets with call-site evidence.
- Multiple call sites to one target remain available under that relationship.
- Ambiguous, external, and unresolved observations are not silently converted into resolved callees.
- The response contains no transitive descendants.
- A known entity with no calls returns a successful empty result.

### 9.3 Backward calls

```http
GET /reverse-callers-query-graph?entity=opaque-entity-key
```

#### Purpose

Return what directly calls the selected current entity.

#### Required behavior

- `entity` is required and must be a current entity key.
- The response identifies the target entity.
- `callers` contains unique direct repository callers with call-site evidence.
- Exact callers and possible ambiguous callers are clearly separated or labeled.
- The response contains no transitive ancestors.
- A known entity with no callers returns a successful empty result.

## 10. Shared Response Behavior

The existing response envelope remains the product convention:

```json
{
  "success": true,
  "endpoint": "/code-entities-search-fuzzy",
  "data": {},
  "tokens": 234
}
```

Every successful response must also identify the current capture used for the answer inside `data`:

- `capture_revision`: monotonic identifier for the running daemon's committed current state.
- `captured_at`: timestamp of the last committed update represented by the response.

All collections must be deterministically ordered so identical capture state and input produce identical output.

### Error behavior

The three endpoints use a consistent failure envelope with a stable machine-readable error code.

Required errors include:

- `invalid_query`: missing or empty fuzzy query.
- `invalid_entity`: missing or malformed entity parameter.
- `entity_not_found`: key is not present in the current capture.
- `capture_not_ready`: initial capture has not been committed.
- `capture_unavailable`: the current capture cannot be read safely.

An entity key removed by a daemon update must return `entity_not_found`; the server must not silently answer from stale state.

## 11. Initial Capture Behavior

When the daemon starts for a repository, it must:

1. Resolve and normalize the repository root.
2. Load ignore rules and configured file constraints.
3. Discover all candidate files.
4. Assign every discovered file a capture state.
5. Detect the language for supported files.
6. Read each file into one immutable source snapshot used for parsing, hashing, and persistence.
7. Parse and extract RootSpans, entities, comments, source-ledger segments, and call observations.
8. Classify every supported source byte as interface code, comment, or unknown code.
9. Resolve internal direct calls where evidence permits.
10. Calculate the expected capture manifest and validate internal referential integrity.
11. Persist the proposed state and independently calculate database totals inside one transaction.
12. Commit only when calculated and persisted manifests match exactly.
13. Print or emit the indexing and accounting report.
14. Begin serving the three query endpoints from that capture.

Before step 12 completes, query endpoints return `capture_not_ready`. They must not expose a partially built repository.

## 12. Daemon Update Behavior

The daemon owns freshness. There is no public watcher-status or manual-reindex HTTP API.

### Required file events

- File creation.
- File content modification.
- File deletion.
- File rename or move.
- Relevant ignore-rule changes.

### Reconciliation requirements

- Bursts of filesystem events may be debounced into a single update batch.
- A changed file is content-hashed so duplicate events are idempotent.
- Deleted entities and their outgoing and incoming edges disappear from the new current state.
- Changed declarations trigger enough call re-resolution to avoid retaining invalid cross-file edges.
- A committed incremental state must be behaviorally equivalent to a clean full capture of the same filesystem state.
- Queries running during an update continue reading the previous committed capture.
- Queries switch to the new revision only after the full update batch is valid.
- A watcher overflow, daemon restart, or suspected missed event triggers filesystem reconciliation.
- The daemon never depends solely on an uninterrupted watcher event stream for correctness.

### Parse failure during update

If a changed file becomes unreadable or cannot be parsed safely:

- The daemon must not continue presenting its previous entities as unquestionably current.
- Safely recovered entities may remain with degraded quality metadata.
- Every readable byte must still be represented as interface code, comment, or unknown code.
- Incomplete, dangling, or malformed bytes must remain queryable through CLI ledger inspection as unknown code.
- Unrecoverable entities and relationships are removed from the committed current graph.
- The failure is visible in daemon logs or CLI status output.
- Other valid files remain queryable.

## 13. Correctness Principles

The MVP prioritizes graph correctness and freshness over breadth or benchmark marketing.

### Required principles

- Never invent a resolved call edge without source evidence.
- Never silently retain an edge whose source or target was deleted.
- Never use line number alone as entity identity.
- Never hide a supported file that failed capture.
- Never return a half-applied repository update.
- Never label ambiguous dynamic dispatch as exact.
- Prefer an explicit unresolved observation over a confident false edge.
- Never classify a byte into more than one primary accounting class.
- Never omit a byte merely because its syntax is malformed or unknown.
- Never commit a revision when calculated and persisted capture manifests differ.
- Produce deterministic results from deterministic input.

### Language support rule

A language counts as supported by this product only when its adapter passes golden fixtures for:

- Entity extraction.
- Nested ownership.
- Forward calls.
- Backward calls.
- Imports and cross-file call resolution appropriate to that language.
- Create, modify, delete, and rename reconciliation.
- Malformed or partially written source files.

The PRD does not expand language support merely by recognizing a file extension. Existing Parseltongue language adapters may be retained, but each must satisfy this narrower call-graph contract before being advertised as supported.

## 14. Acceptance Requirements

### PRD-CAPTURE-001: Initial current state

**WHEN** Parseltongue starts against a valid fixture repository
**THEN** it SHALL discover every non-ignored candidate file
**AND** SHALL assign every discovered file a capture state
**AND** SHALL publish one atomic current capture
**AND** SHALL serve no partial capture before publication.

### PRD-LEDGER-001: Exact three-class accounting

**WHEN** Parseltongue captures a supported readable source file of N bytes
**THEN** it SHALL partition [0, N) without gaps or overlaps
**AND** every byte SHALL be classified as `INTERFACE_CODE`, `COMMENT`, or `UNKNOWN_CODE`
**AND** the sum of those three classes SHALL equal N.

### PRD-COMMENT-001: Comments remain separate

**WHEN** a confirmed comment occurs inside or outside a recognized RootSpan
**THEN** its bytes SHALL be classified as `COMMENT`
**AND** those bytes SHALL not also be counted as `INTERFACE_CODE`.

### PRD-UNKNOWN-001: Incomplete code remains captured

**WHEN** source contains dangling, malformed, unsupported, or otherwise unclaimed bytes
**THEN** those bytes SHALL be retained as `UNKNOWN_CODE`
**AND** relevant parser diagnostics SHALL be attached without introducing another primary byte class.

### PRD-PERSIST-001: Calculated state equals persisted state

**WHEN** a capture revision is proposed
**THEN** its calculated source totals, class totals, hashes, and derived-record counts SHALL match the independently read persisted totals
**AND** any mismatch SHALL abort the transaction
**AND** the previous committed revision SHALL remain readable.

### PRD-CLI-001: Indexing produces an accounting result

**WHEN** a user runs the indexing CLI
**THEN** it SHALL report calculated and persisted totals
**AND** SHALL show interface-code, comment, and unknown-code bytes
**AND** SHALL show calculated and persisted counts for every captured database relation
**AND** SHALL identify every failed invariant
**AND** SHALL support deterministic machine-readable output.

### PRD-SEARCH-001: Search to entity key

**WHEN** a user searches with an approximate entity name
**THEN** fuzzy search SHALL return deterministically ranked current matches
**AND** every match SHALL contain an opaque entity key and current source location.

### PRD-FORWARD-001: Direct callees only

**WHEN** a user queries forward calls for a current entity key
**THEN** the endpoint SHALL return only direct call observations
**AND** SHALL attach source evidence
**AND** SHALL distinguish resolved, ambiguous, external, and unresolved observations.

### PRD-BACKWARD-001: Direct callers only

**WHEN** a user queries backward calls for a current entity key
**THEN** the endpoint SHALL return only direct callers
**AND** SHALL attach the call-site evidence from each caller
**AND** SHALL distinguish exact callers from possible ambiguous callers.

### PRD-DAEMON-001: Incremental equivalence

**WHEN** files are created, modified, deleted, or renamed
**THEN** the daemon SHALL converge to a new committed capture
**AND** that capture SHALL produce the same three API results as a clean full capture of the resulting repository.

### PRD-DAEMON-002: Atomic reads

**WHEN** a query overlaps a daemon update
**THEN** the query SHALL read either the complete previous revision or the complete next revision
**AND** SHALL never combine both.

### PRD-IDENTITY-001: Line-shift stability

**WHEN** unrelated lines move above an otherwise unchanged entity
**THEN** the entity SHALL retain its key
**AND** its returned source location SHALL update.

### PRD-DELETE-001: No stale graph data

**WHEN** an entity or call site is deleted
**THEN** it SHALL disappear from the next committed fuzzy, forward, and backward results
**AND** an obsolete entity key SHALL return `entity_not_found`.

### PRD-DEGRADED-001: Honest partial understanding

**WHEN** the parser can observe a call but cannot resolve a defensible target
**THEN** the system SHALL preserve it as ambiguous, external, or unresolved
**AND** SHALL not publish a fabricated resolved relationship.

### PRD-SURFACE-001: Exactly three endpoints

**WHEN** the MVP HTTP surface is inspected
**THEN** it SHALL expose only the three query routes defined in this PRD
**AND** operational controls SHALL remain internal or CLI-based.

## 15. Test Strategy Required by the Product

### Golden language fixtures

Each advertised language needs small repositories with known entities and call relationships, including:

- Same-file direct calls.
- Cross-file direct calls.
- Methods and constructors.
- Overloads or same-named functions.
- Nested functions attributed to their owner.
- Aliases and imports.
- External calls.
- Ambiguous dynamic calls.
- Syntax errors and partially typed files.
- Comments inside and outside RootSpans.
- Comment-like text inside strings that must not be classified as comments.
- Dangling syntax and unclaimed source classified as unknown code.
- Zero-width missing-node diagnostics.

### Source-accounting fixtures

For every advertised language, tests must prove:

- The three byte classes reconstruct the exact original source.
- Comment bytes take precedence over RootSpan ownership.
- Direct member overlays do not double-count container bytes.
- Error and unknown regions remain present.
- Calculated class totals match persisted class totals.
- Segment hashes match their persisted source slices.
- UTF-8, CRLF, empty files, comments-only files, and incomplete files retain exact byte coverage.

### Daemon convergence fixtures

For every supported language, tests must compare incremental results with a clean rebuild after:

- Adding a caller.
- Removing a caller.
- Renaming a callable.
- Moving lines without changing the callable.
- Moving a file.
- Deleting a file.
- Changing an import or alias.
- Temporarily writing malformed source and then repairing it.
- Simulating duplicate or missed watcher events.

### API contract tests

- Exactly three registered public routes.
- Stable response envelope.
- Deterministic search ranking.
- One-hop-only forward and backward responses.
- Evidence on every internal relationship.
- Correct empty results.
- Correct stale-key and not-ready failures.
- One capture revision per response.

### CLI contract tests

- Index output contains the committed revision.
- Human-readable totals reconcile exactly.
- JSON output follows a versioned deterministic schema.
- Deep verification detects a deliberately corrupted source blob, segment range, segment hash, or row count.
- Accounting mismatch prevents publication.
- Unknown code produces a visible warning or diagnostic, not an accounting failure.

## 16. Capture and API acceptance (in addition to graph-quality evaluation)

The capture subsystem is acceptable when:

1. A user can complete the search-forward-backward loop without another endpoint.
2. Every advertised language passes its golden call-graph fixtures.
3. Incremental daemon state matches clean-rebuild state in convergence tests.
4. Deleted or changed code does not remain silently visible as current.
5. Users can inspect source evidence for every internal relationship.
6. The product makes uncertainty visible instead of overstating static-analysis accuracy.
7. The HTTP surface contains exactly three public routes.
8. The CLI proves that calculated and persisted source totals match.
9. Every supported readable source byte is classified as interface code, comment, or unknown code.
10. Users can locate unknown-code ranges without requiring another HTTP endpoint.

Raw query speed, repository size, number of entities, and number of supported file extensions are guardrails, not product-market-fit metrics. No performance claim should be made until a reproducible benchmark and target repository class exist.

## 17. Backend Neutrality

This PRD defines observable behavior, not storage architecture.

The current capture may be implemented with in-memory graphs, SQLite, Turso, RocksDB, Neo4j, another graph library, or a combination. The choice must not change:

- Endpoint names.
- Request parameters.
- Response semantics.
- Entity identity behavior.
- Resolution-state behavior.
- Atomic capture behavior.
- Incremental-versus-clean equivalence.
- Three-class byte-accounting semantics.
- Calculated-versus-persisted equality.
- CLI report semantics and machine-readable schema.

Backend selection belongs in an architecture decision record, not in this product contract.

## 18. Preparing for Future Architecture Diffing

The MVP does not build architecture diffing, but it should avoid choices that make diffing needlessly destructive later.

The following foundations are useful now and required by the current product anyway:

- Stable entity keys that do not depend on line position.
- Deterministic capture from the same repository state.
- Source hashes and precise evidence spans.
- Monotonic current-capture revision metadata.
- Explicit additions and removals during daemon reconciliation.
- A backend-neutral entity and call-edge model.

The following are explicitly deferred:

- Persisting multiple captures.
- Matching entities across commits after renames or moves.
- Computing added, removed, or changed architecture nodes and edges.
- Rendering a Git or pull-request architecture diff.
- Assigning review risk or trust scores.

Future diffing should consume the stable current-state model created here. It must not expand the current MVP API before this three-query loop is demonstrably reliable.

## 19. Final product boundary

The acceptance test is not merely "can I get my callers?" It is: **can a programmer move from an externally usable Rust contract to the contracts it relies on, back to who relies on it, and down to source where the map is silent or uncertain?** An exact ledger proves the source was captured; independent held-out evaluation tests whether the map is right. For implementation choices and tradeoffs, see the [architecture](Arch-v202607210.md) and [model experiment](../../docs-lossfunk/01-small-model-interface-graph-research.md).
